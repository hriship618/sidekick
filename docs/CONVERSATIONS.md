# Task conversations and app discovery

Sending from the command bar opens one conversation, which stays visible while the work continues. Follow-ups reuse the same message view, composer and native window position. A visible conversation focuses the reply field when input is needed. If the user dismisses it, later questions use a quiet Windows notification rather than forcing the window open. Each question has an identity, so updates cannot repeatedly notify or steal focus. Escape hides the chat without cancelling the task; the hotkey, companion or notification can reopen it. Windows notification delivery still depends on system notification settings.

Exact greetings and thanks have a local response path with no provider call or OS tool action. Narrow informational requests use one model call with a small `reply` schema, without loading the desktop/browser tool catalog. Other conversational messages can use `reply` in the normal agent path without being forced to execute an OS action. Recognized computer-action requests cannot substitute an unverified chat reply for tool execution. General cloud-generated replies still depend on provider/model latency; local greeting speed is not a claim about provider TTFT or streamed generation.

User requests, assistant questions, user answers and final results are stored in local SQLite messages. Technical tool activity remains in expandable execution details. After a task finishes, the composer accepts a follow-up linked to the previous conversation. Up to eight linked task segments and the latest 80 messages are displayed. The model receives at most ten prior messages, each capped at 1,200 characters, in its dynamic context. Old window IDs and old authorization are not reused as fresh execution state.

The narrow `sidekick:follow-up` IPC validates a task UUID and command. Only the main window can call it; the companion's smaller IPC allowlist is unchanged. A follow-up cannot start while another task is running. As before, model-bound conversation text is sent to the configured provider, while local history and evidence persist on the machine.

For `open <app>` requests, the Windows worker builds an app catalog from Start apps plus Desktop and Start-menu shortcuts. It reads executable product/description metadata and package identities. Generic parent-folder words are excluded: Rove living inside a folder named Codex is not evidence that Rove is Codex. The catalog stays warm for five minutes in the owned worker. Requested product names are resolved against current app evidence; no Codex-to-ChatGPT alias is hardcoded. Ambiguous matches ask once, and an explicit selection is remembered by app identity for later matching requests.

Launches use an observed opaque application ID. The worker opens the observed shortcut or validated Windows package identity, rather than constructing an executable path from model text. Launch results say `dispatch-only`: app readiness and successful remote sessions are not inferred from process dispatch. Existing straightforward URL opens and saved routines retain their own routes. Unfamiliar phrasing and contextual follow-ups go to the model.

Tests cover one-popup-per-question behavior, message retention and bounded follow-up context, product/package matching across different display names, Unicode names, and rejecting irrelevant parent-folder matches. The disposable-profile Electron check verifies native visibility and reply focus, Escape without cancellation, persisted replies, a real follow-up action, and renderer recovery. A Windows read-only discovery test on the development machine uniquely identified Codex via its ChatGPT Start entry; a separate launch request was exercised without claiming readiness verification.

Reusable skill/tool packs are a separate extension. See [PLUGINS.md](PLUGINS.md); no importer or MCP runtime is claimed to ship with this update.
